    與 AI 協作的三條防線

    1. 黃金樣本不得由 AI 生成或修改　AI 生成的樣本會自動與 AI 的實作對齊，驗收就失去意義。實作與樣本不符時，預設是實作錯。
    2. AI 不得宣告「L2 通過」　它可以產生 diff 報告，判定權在你。
    3. 每週一次不看程式碼的走查　只照劇本從頭走一遍。這是唯一能發現「每個模組都對、合起來很怪」的方法。

    到期未完成：砍功能，不砍品質

    由上往下砍：① XP Stats 等級連動 → ② 重複 claim 偵測（降級為記警告）→ ③ Skill XP 回寫 → ④ Principles / Domains 讀取

    絕對不砍：L1 契約驗收、L2 判定、步驟 9 與 11（雙寫收斂）。 砍掉這些，這個階段就退化成「接通」——而那正是要避免的事。

    核心架構判斷：Obsidian 是底層，coOS 是高階介面

    Obsidian 不被取代、不被搬空、不進入維護模式。它是 System of Record；coOS 是 Interface & Runtime。

    coOS — 高階介面層 Interface & Runtime
    感測 · 對話 · 邊緣推論 · 草稿生成 · 即時心理狀態機
    擁有：raw_tracking_logs / intent_logs / chat_transcripts / Persona 狀態
    性質：高頻 · 短生命週期 · 可重建 · 隱私敏感
    ↑ 讀治理誰是我 · 我信什麼 · 我在哪個人生階段
    ↓ 寫事實核准後才寫 · append-only · 可撤銷
    Obsidian Vault — 底層 Substrate / System of Record
    Governance　Vision → Domain → Role → Skill → Principle
    Executive　　Project · Event · Routine · Period
    Resource　　 Concept · Artifact · Input · People · Media
    擁有：身分 · 原則 · 技能樹 · XP 帳本 · 長期記憶
    性質：低頻 · 永久 · 純文字 · 可攜 · 不依賴任何 app

    底層缺的：輸入頻寬

    Vault 的設計沒有問題——欠缺的是「所有事實都得由人手動敲進去」。 所以它死於記錄疲勞：日記 9→20→18→6→1→2，XP 紀錄 5 月只剩 2 條。

    高階介面缺的：身分本體

    coOS 有極強的輸入頻寬（OS 遙測 / VS Code 熵 / Git / 瀏覽器 / 對話）， 但冷啟動時 role 空、goals 空、heatmap 回 []。兩者恰好互補。

    定位聲明建議改寫

    原：「不是 Notion / Obsidian 競品。我們不存儲使用者的內容，我們建模使用者的狀態。」
    改：「coOS 不重建個人知識庫。它把 Obsidian Vault 當作身分與長期記憶的底層，自己負責感測、對話與即時心理狀態——Vault 記錄我是誰，coOS 負責照顧今天的我。」

    分層契約：底層與高階介面的邊界

    先看兩層概念如何對應，再定義誰擁有什麼、怎麼互通。

    所有權矩陣：任何一筆資料只能有一個 owner

    另一層只能讀，或提議。

    三條鐵律

    1. append-only 且可撤銷　只 append 到既有區塊，不改既有行；所有寫入帶 coos_generated: true，可用一條 Dataview 全數查出並刪除。
    2. 未經 is_reviewed = true，一個字都不准進 Vault　同時滿足 [R08 §六.1 IKEA] 與「Vault 只收乾淨資料」。
    3. L1 明文永不寫入 Vault　Vault 有 obsidian-git 做 GitHub 同步—— 寫進去等同上雲。這比 M4.7 SPEC 現有的「偵測 iCloud / Dropbox 就警告」嚴格得多， 因為你的 Vault 本來就在同步。

    整合機制：沿用底層既有的事件匯流排，不要發明新的

    Vault 已經有一套跑了半年的模式：calculateRPGStats.js 偵測升級 → 寫 .level_up_trigger.json → level_up_notifier.py watch 並生圖寄信。

    為什麼這樣接

    不需要 Tauri fs 權限　Python sidecar 只讀寫 JSON，.md 的實際修改由 Vault 自己的 JS 完成—— 寫入 Vault 的永遠是 Vault 自己的程式，格式一定合乎契約。
    天然的第二道 Draft & Approve　applyCoosInbox.js 做成 QuickAdd 指令， 你在 Obsidian 裡按一下才落地，符合 [R08 §五 意圖脫鉤]。
    離線安全　coOS 沒開時 Vault 照常運作；Vault 沒開時 coOS 照常收集。兩層鬆耦合。
    衝突處理　全部 append-only 天然無衝突；若目標區塊不存在（模板改版）， 寫進 .coos_inbox/_failed/ 並發 Notice，不靜默失敗。

    對照：M4.7 SPEC 目前的設計為何不能用

    SPEC §7.3 輸出 {vault}/coOS/2026-06-03_csie.md，純標題 + 條列，沒有 frontmatter。 Vault 靠 Dataview 組裝所有視圖（Role 頁查 contains(related_roles, this.file.link)、 Daily 頁查 contains(daily_link, …)），沒有 class: / related_roles: 的檔案 不會被任何一條查詢撈到——寫入即死檔。

    附帶：§7.4 的 PII 正則 [一-鿿]{2,3}(?:小|大|老)\w 匹配不到「陳小明」 （2–3 個中文字後必須緊接 小/大/老），所以 §6 的驗收測試 assert "陳小明" not in content 會失敗； 反而「專題小組」會被誤殺。

    被錯過的最大資產：Governance/Principles（6 條）

    它們不是勵志格言，結構是 The Logic（為什麼有效）→ The Algorithm（IF-THEN-ELSE）→ Anti-Patterns（已知失敗模式）。

    例：「最小可行迭代法則」的 Algorithm 是 IF（我發現自己在看第 3 個教學影片卻還沒寫一行 code）THEN（關掉瀏覽器／寫最爛的一段 code／讓程式報錯）。

    這正是 M1.5 微 Nudges 需要的規則，而且是使用者自己在冷靜時訂下的—— AI 引用「這是你自己說的」可以繞過心理阻抗 [R03 §4]，比任何 LLM 生成的說教都有效， 同時也是 [R16: MI §Rolling with Resistance] 的理想輸入。

    你自己系統的衰減曲線 = coOS 存在的理由

    Obsidian Vault 的實測資料。這是「記錄疲勞」最有說服力的前測證據，目前沒有寫進任何一份 coOS 文件或論文。

    為什麼這件事很重要

    Vault 的日記模板已經非常接近 coOS 的草稿與核准設計：13 條 Routine 預先填好、 4 個 Dataview 區塊自動生成、使用者只需填 Highlights / Improvements 兩欄。

    它在四個月內從每月 20 篇掉到 1 篇。最新一篇（2026-06-25）的 mood／energy／productivity 全空、total_xp: 0、 13 個 checkbox 全未勾、Save Point 反思區塊空白。

    推論：外部審查的魔鬼代言人指出的「審核疲勞」不是理論假設—— 你已經有一份 N=1 的實測資料顯示，把摩擦從「寫」搬到「填兩欄」不足以阻止衰減。 coOS 若要成立，需要的是摩擦預算控制器（系統主動限制自己索取的時間）， 而不是再加一層外在獎勵。

    學術價值：把這條曲線寫進期末報告，能同時解除審查報告的 C1（證據—結論落差） 與 M2（確認偏誤）——因為你先呈現了自己的失敗，而非只呈現對自己有利的詮釋。
