# Phase 1（底層接通）範疇與驗收契約

**版本**：draft — 待拍板
**日期**：2026-08-08
**前置**：`DESIGN_PHILOSOPHY_AUDIT.md`（尤其 §3 分層架構、§3.7 雙寫與收斂）
**要回答的問題**：**怎麼確保這一階段的範疇不失控、做出來的東西符合我的想像、而且品質不只是「接通了」？**

---

## 0. 這份文件的三個機制

| 機制 | 解決什麼 | 章節 |
| --- | --- | --- |
| **想像外化四件套** | 「我要的東西」只存在腦裡，所以無法被驗收，也無法被否證 | §2 |
| **四層驗收階梯** | 目前的 Definition of Done 停在「測試通過」，這只證明程式符合自己寫的規格 | §3 |
| **範疇凍結 + 停車場 + 砍尾巴規則** | 做著做著就長出新功能，最後每件事都做了一半 | §4.5 / §7 |

**一句話**：**先把想像變成可以被打臉的檔案，再開工。**

## 1. 為什麼「接通」不等於「做好」——先看現況診斷

coOS 目前所有 Phase Closure 的驗收都停在同一層：

| Closure Report | 驗收長什麼樣 |
| --- | --- |
| Phase 2 | 「149/149 測試通過」 |
| Phase 4_5 | 「407 passed / 0 failed」 |
| Phase 5.5 | 「446 passed / 0 failed / 7 skipped」 |
| MVP E2E | 「8 步驟中 7 步完整通過」 |

外部審查已經指出這是循環論證：**「我的驗收標準 = 測試通過，測試通過 = 我達標」**。

更直接的證據是 `docs/manual_test_log.md`。裡面每一條抱怨——

- 首次問候 121 字，「一般人打招呼不會這樣」
- 「目前測試到的人格都會有種很急迫、催促的語氣……沒有共情、沒有溫度」
- 「氣泡延遲渲染間隔太短了，應該模擬字數以及打字速度計算時間」
- 「幾乎每次回覆完都產生一個標記」
- 「返回後先前有泡泡斷開的訊息框都被合在一起了」

——**全部都通過了 446 個測試**。它們不是 bug，是**保真度 (fidelity) 與體感 (felt quality) 的失敗**，而現有的驗收裝置完全看不見這一層。

所以問題不在於測試不夠多，而在於**只有一層驗收**。

## 2. 開工前必須先產出的四件套（想像外化）

> 鐵則：**這四件套完成前，一行實作程式碼都不准寫。** 它們不是文書工作，它們就是規格。

### 2.1 逐字劇本 (Demo Script) — `docs/phase1/DEMO_SCRIPT.md`

不是 SPEC，是**劇本**。用第一人稱寫「我會看到什麼、我會打什麼字、系統會回什麼」，包含**實際的文字內容**而非佔位符。

寫劇本的三條規則：

1. **必須有具體字串**。不可以寫「系統顯示問候語」，要寫出你希望看到的那一句：
   `「哈囉！我是嚴鋒，矽谷的技術架構師。聽說你要做生成式 AI 的期末專案？」`（41 字，對照你自己在 manual_test_log 寫的理想版本）
2. **必須有「不該發生什麼」**。例如：*「這一步不應該出現任何 project 偵測標記，因為我還沒講到專案。」*
3. **寫不出來 = 還不知道自己要什麼**。這時該做的是先手畫 / 先用 Obsidian 手動模擬一次，不是先寫程式。

劇本是後續 L2 驗收的**唯一比對基準**。

### 2.2 黃金樣本 (Golden Fixtures) — `testing/golden/phase1/`

對 Phase 1 每一種輸出，**手寫**一份「理想長什麼樣」的檔案存進 repo：

| 檔案 | 內容 |
| --- | --- |
| `golden_daily_savepoint.md` | coOS 寫回 Daily note 的 Save Point 區塊，理想的樣子（含 frontmatter、`coos::` 標記、字數） |
| `golden_skill_xp_line.md` | 寫回 Skill note 的 XP 行，逐字 |
| `golden_capture_spark.md` | 從 coOS 捕捉的靈感落到 Inbox / Sparks 區塊的樣子 |
| `golden_role_import.json` | M4.7a 讀完 Vault 後，coOS 端 role 物件應該長什麼樣（含 mission 全文） |
| `golden_reflection_card.json` | 一張日報草稿卡的理想欄位與長度 |

> **鐵則：黃金樣本不得由 AI 生成。** 由 AI 生成的黃金樣本會自動與 AI 的實作對齊，驗收就失去意義。這是整份文件裡最重要的一條紀律。

### 2.3 反例清單 (Anti-Examples) — `docs/phase1/ANTI_EXAMPLES.md`

把「我不要的東西」寫成可測條件。`manual_test_log.md` 已經是一份現成的反例清單，只需要把它變成斷言：

| 反例 | 可測條件 |
| --- | --- |
| 問候太長 | `len(greeting) <= 40` |
| 一個氣泡塞多個問題 | `greeting.count("？") <= 1` |
| 語氣急迫催促 | 不得包含 `別浪費時間`、`與其…不如`、`既然你…就直接` 等模式 |
| 寫回 Vault 的檔案撈不到 | 寫入後執行一次 Dataview 等價查詢，必須撈得到該筆 |
| 重複計算 XP | 同一 `coos::` id 重放兩次，`total_xp` 不變 |
| 汙染 Vault | 寫入的所有內容經一次 `git diff`，不得出現任何 L1 明文片段 |

反例比正例好用，因為它們**不需要你想清楚要什麼，只需要你認得出什麼不行**。

### 2.4 基線量測 (Baseline) — `docs/phase1/BASELINE.md`

**動工前先跑一次**，否則做完無從比較。至少四項：

| 指標 | 取法 |
| --- | --- |
| Vault 衰減曲線 | Daily 篇數 / 月、Skill XP 條數 / 月（已有：9→20→18→6→1→2；86→86→44→35→2→15） |
| coOS 現有草稿核准率 | `daily_reflections` 中 `is_reviewed=1` / 全部 |
| coOS 每日互動分鐘數 | `raw_tracking_logs` |
| 冷啟動空白程度 | 目前 roles / goals / promises / heatmap 各回傳幾筆（已知：多為 `[]`） |

## 3. 四層驗收階梯 (Acceptance Ladder)

這是本文件的核心。每個交付物都要爬完四層，**而不是通過 L0 就宣告完成**。

| 層 | 名稱 | 問題 | 誰驗 | 工具 | 可自動化 |
| --- | --- | --- | --- | --- | --- |
| **L0** | **接通** Wiring | 端到端跑得動嗎？ | CI | pytest / vitest | ✅ 完全 |
| **L1** | **契約** Contract | 輸出符合形式規格嗎？ | CI | schema 驗證 + Dataview 等價查詢 + 冪等重放 + `git diff` 檢查 | ✅ 完全 |
| **L2** | **保真** Fidelity | 輸出跟我想的一樣嗎？ | **人**（不可授權給 AI） | 對照 §2.1 劇本與 §2.2 黃金樣本，逐項 diff | ⚠️ 半自動 |
| **L3** | **體感** Felt Quality | 我真的願意每天用嗎？ | **人 + 數據** | 連續使用 7 天 + §2.4 基線對照 | ❌ 只能實測 |

### 3.1 各層的具體判準

**L0 接通**——現有做法，維持即可。新增要求：每個新模組的測試必須包含至少一個**失敗路徑**（Vault 路徑不存在、日記檔不存在、區塊不存在），不能只測 happy path。

**L1 契約**——Phase 1 特有，全部可自動化：

```
□ 寫入 Vault 的檔案，執行等價 Dataview 查詢能撈到
□ 所有 coOS 寫入行都帶 [coos:: <id>]
□ 同一 payload 重放 3 次，Vault 檔案的 diff 為空
□ 撤銷查詢 (WHERE coos != null) 能找出全部 coOS 寫入
□ 未 is_reviewed 的內容，Vault 中查無此筆
□ git diff 中不得出現 chat_transcripts / raw_text 任何片段
□ 手動在 Obsidian 改一筆 Role/Skill/Project，coOS 重掃後狀態同步
□ coOS 完全關閉時，P1（Templater/QuickAdd）與 P2（iOS 捷徑）功能不受影響
```

**L2 保真**——**人工，且必須留下紀錄**。做法：

1. 照 §2.1 劇本從頭走一遍，每一步截圖
2. 每個輸出與 §2.2 黃金樣本並排 diff
3. 填一張表：

   | 步驟 | 黃金樣本 | 實際輸出 | 判定 | 差異描述 |
   | --- | --- | --- | --- | --- |
   | 3 | （貼上） | （貼上） | ✅ / ⚠️ / ❌ | |

4. **判定為 ⚠️ 或 ❌ 的，不准以「之後再優化」帶過**——要嘛修，要嘛明確寫進停車場並標註「本階段接受此差異，理由是 ___」

**L3 體感**——連續使用 7 天，每天記三個數字（30 秒就能填完，別做成問卷）：

| 欄位 | 尺度 |
| --- | --- |
| 今天我是自願打開 coOS 的嗎？ | 是 / 被提醒才開 / 沒開 |
| 核准那張卡花了幾分鐘？ | 分鐘數 |
| 寫完之後我覺得？ | 值得 / 沒感覺 / 像交作業 |

搭配自動數據：核准率、草稿→核准延遲、`user_feeling` 字數。

> **L3 不設通過門檻**，它的用途是產生 §5.1 需要的證據，並在下一階段當基線。但**若 7 天中有 4 天以上是「沒開」或「像交作業」，Phase 2 的第一件事必須是回頭修這個，而不是加新功能。**

### 3.2 Definition of Done

> **Phase 1 完成 = L0 全綠 ∧ L1 全綠 ∧ L2 全部判定為 ✅ 或已明確記錄的可接受差異 ∧ L3 已有 7 天數據。**

四項缺一，就不寫 Closure Report。

## 4. Phase 1 範疇（草案，待你拍板）

### 4.1 一句話目標

> **讓 coOS 讀懂 Vault 裡的「我是誰」，讓一次已核准的反思真的落回 Vault，而 Vault 仍然可以被我獨立手動編輯。**

注意這句話的三個子句對應 §3 分層架構的三個方向：**讀治理**、**寫事實**、**雙寫收斂**。

### 4.2 唯一的垂直切片（這就是 §2.1 劇本的骨架）

按模組分 Phase 會做出「每個模組都通了、但沒有一條路走得完」。Phase 1 只認一條路：

```
 1. 開 coOS  → 側欄出現 Vault 裡真實的 10 個角色（含 mission），不是 demo 資料
 2. 選「🔬 大學專題生」→ 看到屬於這個角色的真實 active 專案
 3. 跟一位專家聊 10 分鐘 → 對話進 chat_transcripts，Observer 偵測到主題
 4. 隔天 02:00 → 草稿卡生成
 5. 我填「主觀感受」與「行動計畫」→ 核准
 6. 打開 Obsidian → 今天的 Daily note 的 Save Point 區塊多了一段，帶 coos:: 標記
 7. 對應的 Skill note 的 Experience Log 多一行 - YYYY-MM-DD: +N XP (…) [coos:: …]
 8. XP Stats 頁面的等級跟著動
 9. 我在 Obsidian 手動新增一個 Skill、把一個 Project 改成 on_hold → coOS 重掃後看得到
10. 我在 Obsidian 手動 claim 了同一天同一技能的 XP → coOS 在下一張卡上問我是不是重複，不自動加
11. coOS 完全關閉 → 我用 QuickAdd 與 iOS 捷徑照常記錄，一切正常
```

**第 9–11 步是這個階段的靈魂**。只做 1–8 就只是「接通」；9–11 才證明分層架構真的成立。

### 4.5 停車場規則

任何在開發過程中冒出來的新想法——**一律不進本階段**，寫進 `docs/phase1/PARKING_LOT.md`，格式三行：

```
- [想法] ___
  [為什麼現在想到] ___
  [如果現在不做會怎樣] ___
```

第三行是關鍵：**如果答案是「不會怎樣」，那它就該留在停車場。**

## 5. 每一步的三層驗收條件

| # | 步驟 | L0 接通 | L1 契約 | L2 保真（對照劇本 / 黃金樣本） |
| --- | --- | --- | --- | --- |
| 1 | 讀出 10 個角色 | API 回傳 10 筆 | mission 全文無截斷；`role_id` 對得上 Vault 的 `id:` | 側欄呈現與劇本描述一致；emoji 與別名正確 |

| 8 | XP Stats 等級變動 | 數值改變 | 變動量 = 寫入 XP，無多算 | 等級數字與 coOS 端顯示一致（見 §9 公式拍板） |

| 10 | 重複 claim 偵測 | 不 crash | `total_xp` 未重複增加 | 詢問文案符合劇本，且**不是自動決定** |
| 11 | coOS 關閉時 Vault 獨立運作 | — | QuickAdd 6 個巨集全部可用；iOS 捷徑可用 | 手動走一遍，體感無異狀 |

## 6. 與 AI 協作的三條防線

你主要用 Claude Code 實作，這帶來一個特定風險：**AI 會把「符合我寫的規格」誤當成「符合你的想像」，而且它寫測試、寫實作、寫驗收報告都很流暢**——結果是一套自洽但可能整體偏移的系統。

### 防線 1：`CLAUDE.md` 增修三條

```markdown
## Phase 1 專用鐵則

1. 黃金樣本 (testing/golden/) 由使用者手寫，AI 不得新增或修改。
   實作與黃金樣本不符時，預設是實作錯，不是樣本錯。
   若認為樣本有誤，必須停下來問，不得自行修改樣本。

2. L2 保真驗收由使用者判定。AI 可以產生 diff 報告，
   但不得在任何文件中寫「L2 通過」。

3. 任何寫入 Obsidian Vault 的行為必須經 _System/.coos_inbox/ 契約。
   禁止 Python 直接改 .md，禁止呼叫 Templater API。
```

### 防線 2：PR 附「想像 vs 實作」對照

每個 PR 描述必須有這三段（AI 填前兩段，你填第三段）：

```
### 這個 PR 對應劇本的第幾步
### 黃金樣本 diff（貼上）
### 使用者判定：✅ / ⚠️（差異：___）/ ❌
```

### 防線 3：每週一次「不看程式碼的驗收」

一週一次，**不看 code、不看測試報告**，只照劇本從頭走一遍。這是唯一能發現「每個模組都對、但合起來很怪」的方法——`manual_test_log.md` 裡所有有價值的發現都是這樣來的。

## 7. 時程與砍尾巴規則

### 4 週 time-box

| 週 | 產出 |
| --- | --- |
| **W0（開工前）** | §2 四件套 + §9 拍板事項 + 基線量測 |
| **W1** | 文件入憲 + M4.7a Reader（劇本步驟 1、2、9） |
| **W2** | M4.7c 匯流排 + `applyCoosInbox.js`（步驟 6 的骨架 + 步驟 11） |
| **W3** | M4.7b Writer + 冪等去重（步驟 6、7、8、10） |
| **W4** | 全劇本走查 + L1 自動化 + L2 判定 + 開始 L3 七天記錄 |

### 到期未完成時：砍功能，不砍品質

砍的優先序（**由上往下砍**）：

1. 步驟 8（XP Stats 等級連動）——可以延後，寫入正確就好
2. 步驟 10（重複 claim 偵測）——降級為「在 raw_tracking_logs 記警告」
3. 步驟 7（Skill XP 回寫）——保留步驟 6 的 Daily 回寫即可證明分層成立
4. M4.7a 的 Principles / Domains 讀取——先讀 Roles / Skills / Projects

## 附錄：這套方法為什麼能提高「符合想像」的機率

它不保證做出來的東西完美，但它讓**偏移在早期就被發現**：

| 傳統做法 | 偏移何時被發現 |
| --- | --- |
| 寫 SPEC → 實作 → 測試通過 → 用用看 | 全部做完之後 |
| **本方法** | |
| 寫劇本 | 寫不出來時（第 0 天） |
| 寫黃金樣本 | 手寫理想輸出時發現自己也說不清（第 0 天） |
| L1 契約 | 每次 commit |
| L2 保真 | 每個 PR |
| 每週不看程式碼走查 | 每週 |
| L3 體感 | 第 4 週 |

**成本主要落在 W0**，而 W0 的產出（劇本、黃金樣本、反例清單）在後續每個 Phase 都能重複使用——它們才是這個專案真正稀缺的資產，因為它們是**只有你能寫的東西**。
