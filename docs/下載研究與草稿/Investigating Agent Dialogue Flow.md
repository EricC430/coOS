### Planner Response

關於你的三個問題，以下是詳細的設計考量與我們完成的改進：

### 1. 為什麼快取 key 包含 `role_id`？與它有什麼關係？
* **角色隔離（Role Isolation）**：`coOS` 允許使用者動態切換不同的角色（例如「學生」、「軟體工程師」、「休閒玩家」）。不同角色擁有完全不同的系統提示詞、專家性格和意圖邊界。
* 如果快取 Key 沒有包含 `role_id`，當使用者從「軟體工程師」切換成「學生」時，在同一個編輯器視窗下，系統可能會誤判並直接重用上一個角色產生的意圖特徵向量。
* 包含 `role_id` 可以確保當角色切換時，快取會安全地 miss，重新讓對應的邊邊推論模型進行推理，嚴格防止角色間的上下文資訊洩漏（Context Leakage）。

### 2. 為什麼是 5 分鐘？應該 1~2 分鐘吧？
* 你的直覺完全正確！5 分鐘的時間對人的專注切換來說過長了。如果使用者在同一檔案內迅速切換了開發重點，5 分鐘的 TTL 會導致語意更新滯後。
* 我已將 **TTL 縮短為 90 秒（1.5 分鐘）**。這能兼顧「節省邊緣裝置（如 iPad/本地端）的重複推理能耗」與「對使用者活動變化的即時反應度」。

### 3. 為什麼不用比對內容的相似度，而是只有依照時間來看？
* 這是先前版本的不足之處。如果只看時間，即便在同一個檔案內寫了完全不同的程式碼（例如從寫 SQL 移到寫前端代碼），也會因為 window title 一致而造成快取誤擊。
* **改進方案**：我已為快取加入了**文字相似度比對機制**：
  1. 將快取值改為儲存 `(時間戳記, 原始文字內容, IntentVector)`。
  2. 比對時，利用輕量級的字詞 Jaccard 相似度計算比率：
     $$\text{Similarity} = \frac{|A \cap B|}{|A \cup B|}$$
  3. 當且僅當相似度 **$\ge 0.75$（75% 的詞彙重疊度）** 且時間在 90 秒內時，才算快取命中（Cache Hit）。
  4. 若使用者移除了原內容或撰寫了大量新內容，相似度低於 0.75，則會主動觸發快取失效（Cache Miss）並發起新的 LLM 審計與意圖分類。

### 2. 你確定 "Expecting value: line 1 column 1" 的導因是如你所述嗎？還是有其他可能？目前排隊與分發的機制是什麼？會不會是排隊/分發處理不當？

經過對代碼與排隊機制的深度審計，**「Expecting value: line 1 column 1」主要源於「Ollama 輸出格式異常」以及「排隊機制被繞過造成的併發衝突」。**

以下是目前排隊機制、資料流與潛在導因的深度解析：

#### A. 目前的排隊與分發機制（Data Flow）
1. **分發起點**：Gemma 客戶端（`GemmaEdgeClient`）定義了向 Ollama `/api/chat` 發送請求的 `_run_request` 協程。
2. **入隊（Enqueue）**：它不直接執行，而是調用 `enqueue_inference(priority=3, fn=_run_request)`。
3. **優先佇列處理（Priority Queue）**：
   - 佇列採用 `asyncio.PriorityQueue`，按優先級排序（`1=chat (高)`、`2=code_diff (中)`、`3=telemetry_batch (低)`）。
   - 在 FastAPI lifespan 中啟動了一個單一的背景工作線程（`inference_worker`），它會**序列化（Serialized）**地從佇列中取出任務：
     ```python
     task = await global_inference_queue.get()
     res = await task.fn() # 每次只會執行一個 HTTP 請求至本地 Ollama
     ```
   - 這種序列化設計是為了**保護 iPad/行動端邊緣設備的 GPU 與 VRAM 資源**，防止併發推論造成設備崩潰或超時。

#### B. "Expecting value: line 1 column 1" 的三大潛在導因分析

根據這套機制，該錯誤（代表解析空字串或非 JSON 網頁內容時崩潰）有以下三個主要誘因：

| 誘因 | 機制分析 | 解決與優化方案 |
| :--- | :--- | :--- |
| **1. 語意審計（DRIFT Shield M2.3）繞過佇列造成併發** | **現狀：** `DriftShield` 在 `/api/m1_1/event` 中是直接調用 `_run_request()`（見 `drift.py`），**繞過了優先佇列**。 當背景異步 Gemma 壓縮（Priority 3）正在運行時，如果此時用戶輸入觸發了 DRIFT 安全審計，兩者會**併發發送到本地 Ollama**。 iPad 的 Ollama 在併發加載下會出現記憶體不足、連接重置（Connection Reset）或返回 `503 Service Unavailable` 的 HTML 錯誤頁面，導致 `resp.json()` 崩潰並丟出 Column 1 錯誤。 | **優化**：應將 `DriftShield` 的推論也納入優先佇列，並給予最高的 **Priority 1**，確保安全審計能搶佔背景壓縮，但與其保持序列化執行，不發生併發衝突。 |
| **2. Ollama JSON Mode 的局限性與字首干擾** | **現狀：** 雖然設置了 `"format": "json"`，但 Ollama（特別是 4-bit 量化模型）在極端情況下仍可能輸出類似 `Here is the JSON: { ... }` 的說明性字首。這會使 `content` 第一個字元不是 `{`，導致 `json.loads` 拋出 `line 1 column 1`。 | **已修復**：我們實作的 `re.search(r"\{.*\}", content, re.DOTALL)` 正好能完美過濾掉這類說明文字，精準抓取 JSON 塊。 |
| **3. 異步更新時的 SQLite 鎖衝突** | **現狀：** 背景異步任務 `run_gemma_async` 拿到結果後，會每隔 1 秒嘗試讀取並更新 `raw_tracking_logs` 表（共重試 5 次）。如果此時主執行緒正在大量寫入日誌造成資料庫鎖定，可能導致更新超時或異常。 | **現狀評估**：我們已在啟動時啟用了 SQLite 的 **WAL (Write-Ahead Logging)** 模式，這能允許同時讀寫，大大減輕了鎖衝突。 |

### 3. 目前的排隊機制是否有實作 Batch API 形式？

目前系統在**佇列層**與**應用層**採取了不同的批次處理策略：

1. **優先佇列層（Queue Level）**：
   * **沒有**提供類似批次打包多個任務同時發送至 Ollama 的 Batch API。
   * 因為本地/iPad 邊緣端硬體限制，排隊機制的核心目的是將請求「串行化（Serialized）」，每次只處理一個任務，防止 GPU 記憶體溢出（OOM）或硬體超載。
2. **應用層（Application Level / Debouncer）**：
   * **已實作應用層的 Batching**：系統透過 `EventDebouncer` (`M2.1`) 實現了批次處理。
   * **運作機制**：當遙測事件頻繁觸發時，系統不會對每條事件都發起一次 LLM 推論。Debouncer 會在緩衝區中累積事件，當達到時間閾值（依角色設定在 15~60 秒之間）或容量閾值（1000 條）時，會將它們打包成 `EventBatch`。
   * 在 [main.py 的 _m2_2_flush 方法中](file:///c:/Users/chent/Desktop/我的資料夾/學校/大學/三下/生成式人工智慧導論/coOS/services/main.py#L850-L890)，系統會將這批事件轉換成一段總結文字（`summary_text`），然後**只發起一次** `compress` 推論。這是一種極具能效比的客戶端批次化（Temporal Batching）策略。

### 2. 為什麼剛才執行會報錯 `Error: Unknown option '--db-path'`？

這是因為您使用了 **Node.js (NPM)** 來跑 Python 版的指令參數，兩者的實作不同：

1. **Python 版（目前 `.mcp.json` 裡面的設定）**：
   * 使用 **`uvx`**（Python 封裝執行器）來跑，它接受的參數是 **`--db-path`**。
   * 這就是為什麼您設定檔中寫的是：
     ```json
     "command": "uvx",
     "args": ["mcp-server-sqlite", "--db-path", "./data/coos.db"]
     ```
2. **Node.js 版（您在終端機嘗試執行的指令）**：
   * 使用 **`npx`** 來跑，但 Node.js 版的套件只接受 **`--db`** 或 **`--database`**，不認識 `--db-path`。
   * 因此您手動用 `npx` 跑時會噴錯。
